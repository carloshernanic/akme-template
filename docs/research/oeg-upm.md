# Observatório OEG-UPM: ferramentas e estudos do Ontology Engineering Group

Data da rodada: 2026-10-27 (primeira rodada; relatório vigente).
Fonte principal: `gh repo list oeg-upm` (385 repositórios públicos), READMEs e releases via `gh api`, PyPI, páginas do grupo e página de status dos serviços (https://oeg-upm.github.io/oeg-service-status/).
Convenção: afirmações que não consegui verificar diretamente estão marcadas com `needs_validation`.

## 1. Resumo executivo

1. A org oeg-upm tem 385 repositórios, a maioria ontologias de projetos (AURORAL, COGITO, BIMERR), corpora de PLN e material de papers. As ferramentas de engenharia de ontologias relevantes são cerca de 20, e várias das mais importantes vivem fora da org: Widoco (dgarijo), Morph-KGC (org morph-kgc), OnToology (org OnToology), yatter (migrado para citiususc).
2. O ecossistema é organizado pela metodologia LOT (requisitos, implementação, publicação, manutenção), e cada atividade tem ferramenta própria: ORSD e CORAL para requisitos, Chowlk para conceitualização, OOPS!, Themis, Astrea e FOOPS! para avaliação, Widoco e OnToology para documentação e publicação, Morph-KGC, Mapeathor, yatter e RMLdoc para mapeamento de dados.
3. Para o akme-template (Python 3.11, sem Java, sem LLM nas tools) o que entra limpo via pip é: Morph-KGC (tabular para RDF), yatter (YARRRML para RML), RMLdoc (documentação de mapeamentos) e pycottas (opcional). Nenhum exige Java.
4. OOPS!, Themis, FOOPS!, Chowlk e Astrea existem como REST em linkeddata.es, mas a infraestrutura é instável: em 2026-10-27 a página de status do próprio OEG reportava OOPS! e FOOPS! fora do ar (HTTP 500) e 16 de 26 serviços indisponíveis. Toda integração REST precisa ser opcional, com timeout e degradação explícita.
5. OOPS! foi reescrito em 2025 (versão 0.2.0, Apache-2.0, Java 17, Jena) e continua expondo o mesmo contrato REST (POST XML `OOPSRequest` em `/rest`, resposta em Turtle com `oops:pitfall`). É a melhor candidata a validador externo, mas o serviço público está caindo com frequência.
6. Astrea é o caso mais interessante para reimplementar sem Java: o núcleo são consultas SPARQL CONSTRUCT publicadas em CSV e num grafo (Astrea-KG, Apache-2.0) que podem ser executadas com rdflib para gerar SHACL a partir do OWL. `needs_validation` quanto à compatibilidade de todas as queries com o motor SPARQL do rdflib.
7. Themis define uma sintaxe de testes simples (`Sensor subclassOf Device`, `Sensor type Class`) derivada de padrões léxico-sintáticos do corpus CORAL. A sintaxe é reimplementável em rdflib para a tool `eval`; o serviço e o jar ficam como opção.
8. Widoco exige Java 11+ (jars por JDK 11, 14 e 17, cerca de 25 MB) ou Docker. Não há port em Python. Fica como citação, com pyLODE (fora do OEG, pip) como alternativa para o `export`.
9. Chowlk converte diagrama (diagrams.net com notação Chowlk) em OWL, não o inverso. O conversor é Python puro (rdflib, bs4) no branch `webservice`, mas não está no PyPI. Para gerar diagramas a partir de OWL o OEG usa Devos (Mermaid, pip `devos-py`, dependências pesadas e sem release desde 2023) e owl2diagram (jatoledo).
10. Estudos recentes que importam ao template: CQ4OE (benchmark CQ para ontologia, com provenance CQ para termo e CQ para axioma), MASEO (CQs atomizadas via templates CLaRO e geração de testes Themis), Ontology Governance Framework (2026), OWL Change Ontology e OntoRipple (propagar mudanças da ontologia para RML e SHACL), e o paper KCAP 2025 sobre desenvolver OWL e SHACL em conjunto.

## 4. Recomendação de integração

Critérios: `integrar como tool` exige ser determinístico, chamável do Python sem LLM, licença compatível (Apache-2.0, MIT) e sem Java nem Docker na máquina do consultor, ou com REST opcional e degradação explícita. `citar na skill` cobre o que é manual, pesado ou só web. `ignorar` cobre o que está fora de escopo ou parado.

### 4.1 Integrar como tool

| Ferramenta | Tool do akme | Como integrar | Dependência pesada | Justificativa |
|---|---|---|---|---|
| Morph-KGC | `publish`, `export` | `uv add morph-kgc` (extras `[excel]` se houver xlsx; `[postgresql]`, `[mysql]` conforme o `connect`). Gerar YARRRML a partir dos `mappings` do `content.yml`, escrever um INI em memória (`[DataSource1] mappings=...` e `db_url=` ou `file_path=`) e chamar `morph_kgc.materialize(config)` para obter um `rdflib.Graph`, ou `materialize_oxigraph` para grafos grandes. DataFrames podem ser passados em memória como segundo argumento | Nenhuma de Java. Instala pandas, duckdb, pyoxigraph (wheels binários), falcon | Engine Python de referência para RML, ativa, Apache-2.0, aceita YARRRML e as fontes que o `connect` prevê |
| yatter | `publish`, `export` | `uv add yatter`; `yatter.translate(yaml_dict)` devolve RML em Turtle para exportar o mapeamento em formato padrão W3C CG além do YARRRML | Nenhuma | Puro Python, ativo, Apache-2.0; Morph-KGC já lê YARRRML, então yatter serve ao `export` do RML |
| RMLdoc | `export` | `uv add rmldoc`; chamar a CLI `rmldoc -i mapping.rml.ttl -o mapping.md` via `subprocess` ou importar o módulo (`needs_validation` quanto à API pública Python; a CLI é estável) | Nenhuma (rdflib, Jinja2, yatter) | Documenta os mapeamentos em Markdown com diagramas, sem Java |
| Astrea-KG (queries SPARQL) | `validate`, `export` | Vendorizar `material/Queries.csv` ou `Astrea-KG-latest.ttl` do repositório oeg-upm/astrea (Apache-2.0) e executar as SPARQL CONSTRUCT com rdflib sobre `schema.ttl` para gerar shapes SHACL; validar dados com pySHACL (fora do OEG, pip). `needs_validation`: compatibilidade de todas as queries com o motor SPARQL do rdflib e necessidade de resolver `owl:imports` antes | Nenhuma (sem o jar Java) | Reutiliza o conhecimento OWL para SHACL do grupo sem Java nem serviço remoto |
| Sintaxe de testes Themis | `eval` | Reimplementar em rdflib o subconjunto da sintaxe Themis (`A type Class`, `A subclassOf B`, `A P B`, `A P some B`, cardinalidades, `A disjointWith B`) e os veredictos (correto, termo ausente, relação ausente, conflito), gerando testes a partir das CQs e termos do `content.yml`. Opcional: enviar o mesmo arquivo `.txt` ao REST de Themis para cruzar resultados (`needs_validation` para os caminhos do swagger) e exportar em JUnit | Nenhuma na versão nativa; REST remoto na opcional | Mantém compatibilidade com o formato do OEG e com o que MASEO e OnToology produzem, sem Java |
| OOPS! REST | `validate` (opcional, flag `--oops`) | `POST https://oops.linkeddata.es/rest` com `Content-Type: application/xml` e corpo `OOPSRequest` (ontologia em `OntologyContent` via CDATA, ou `OntologyUrl`; `Pitfalls` para filtrar). Parsear a resposta Turtle com rdflib (`oops:hasCode`, `oops:hasImportanceLevel`, `oops:hasNumberAffectedElements`). Antes de chamar, ler `services_status.json` do oeg-service-status e aplicar timeout curto; se indisponível, devolver resultado parcial com aviso. Em paralelo, implementar nativamente em SPARQL os pitfalls estruturais listados na seção 3 | Serviço remoto instável (fora do ar em 2026-10-27). Self host exige Java 17, Maven, Tomcat | Único scanner de pitfalls com catálogo reconhecido; o contrato REST é estável desde 2014 e foi mantido na reescrita 0.2.0 |
| FOOPS! REST | `publish` (opcional, checklist FAIR) | `POST https://foops.linkeddata.es/assessOntology` com JSON `{"ontologyUri": "..."}` após publicar, ou `POST /assessOntologyFile` com o arquivo (`needs_validation` para o formato multipart). Resposta JSON com testes e score. Mesmo esquema de pré-checagem via status e timeout | Serviço remoto (fora do ar em 2026-10-27). Jar de 38.8 MB exige Java 8+ | Checklist FAIR objetivo para a etapa de publicação; sem equivalente em Python |
| Chowlk REST | `ontology_write` (entrada opcional por diagrama) | `POST https://chowlk.linkeddata.es/api` multipart `data=@diagram.xml`; usar `ttl_data`, `errors`, `warnings` e `xml_error_file`. Alternativa sem rede: vendorizar `converter.py` e a pasta `python/` do branch `webservice` (Apache-2.0; só rdflib e bs4) | Serviço remoto (reportado no ar em 2026-10-27, inacessível da minha rede); vendorização traz código de 2025 sem pacote PyPI | Permite que o consultor conceitualize no diagrams.net e o template importe OWL; não resolve OWL para diagrama |
| oeg-service-status JSON | utilitário de `validate` e `publish` | `GET https://raw.githubusercontent.com/oeg-upm/oeg-service-status/main/services_status.json` e checar `status_http_code` de `oops`, `themis`, `foops`, `chowlk`, `astrea` antes de chamar os REST | Nenhuma | Evita timeouts longos e dá mensagem clara ao consultor |

### 4.2 Citar na skill

| Ferramenta | Justificativa e como citar |
|---|---|
| Widoco | Exige Java 11+ ou Docker. Citar o comando `java -jar widoco-1.4.26-jar-with-dependencies_JDK-17.jar -ontFile schema.ttl -outFolder docs -rewriteAll -getOntologyMetadata -uniteSections -webVowl` e a imagem `ghcr.io/dgarijo/widoco:v1.4.26`. O `export` deve emitir os metadados que o Widoco reconhece. Alternativa pip (fora do OEG): pyLODE 3.6 (Python 3.12+, `needs_validation` para 3.11) |
| OnToology | Serviço web com acesso de escrita ao GitHub; citar como caminho de publicação com w3id quando o cliente aceita repositório público |
| Themis (serviço e jar) | Citar o swagger e o jar como validação cruzada dos testes gerados pelo `eval`; jar exige Java |
| Astrea (serviço e jar) | Citar o REST em astrea.linkeddata.es e o Docker `acimmino/astrea-service:2.2.0` como alternativa à execução nativa das queries |
| Mapeathor | Formato de planilha para mapeamentos; útil quando o cliente prefere Excel. Instala Flask mesmo em CLI; o `content.yml` já cobre o papel |
| Devos e owl2diagram | Geram Mermaid a partir de OWL, mas Devos está parado desde 2023 com dependências pesadas (nltk, scikit-learn, seaborn). Recomendar reimplementar no `export` um classDiagram Mermaid via SPARQL (classes, subclasses, propriedades de objeto) seguindo a ideia do Devos |
| OntoRipple e OWL Change Ontology | Ciclo de manutenção: quando `schema.ttl` mudar, registrar mudanças em OCH e usar `ontoripple` (pip, puro Python) para atualizar RML e SHACL. Exige produzir o grafo de mudanças, que o template ainda não gera; candidato a tool em rodada futura |
| LOT, ORSD, LOT-resources, Template-Ontology-Repository, Ontology Governance Framework | Base metodológica da skill: campos do ORSD, layout de pastas do repositório de ontologia, papéis e RACI |
| CORAL | Fonte dos padrões léxico-sintáticos para a tradução CQ para teste; citar os 29 padrões e usar os 12 propostos como tabela de referência na skill |
| CQ4OE e MASEO | Protocolo de anotação CQ para termo e CQ para axioma como método de avaliação; MASEO como referência de atomização de CQs (CLaRO). Ambos usam LLM, então ficam na skill |
| OOPS+ | Pitfalls que exigem LLM (semântica dos rótulos, definições). Citar como etapa manual opcional |
| LOV (lov.linkeddata.es) | Busca de termos para reuso; API `needs_validation` |
| pycottas | Útil só para grafos grandes; citar como opção de armazenamento comprimido para o `export` |
| github-action-morph-kgc e github-action-sparql | Citar como automação em CI para clientes com GitHub |
| SHACLINT | Integração de shapes de múltiplas fontes; nicho, citar |
| Licensius e rdflicense | Catálogo de licenças em RDF para preencher `dcterms:license`; Java e serviço remoto |
| shacl-owl-kcap-2025, llm4oe-slr | Estudos de apoio à decisão (OWL versus SHACL; o que automatizar com LLM) |

### 4.3 Ignorar

| Ferramenta | Justificativa |
|---|---|
| Morph-RDB, Morph-CSV, Helio e módulos, morph-graphql (arquivado) | Java/Scala/Docker, parados, superados pelo Morph-KGC |
| oops-plugin (Protégé), vocabLite, webODE, ShapesToWidocoHTML, OnToologyDnD | Parados, Java, dependem de GUI ou serviços externos |
| ERA-SHACL-Benchmark, kgc-eval, gtfs-bench, lubm4obda | Benchmarks de engines, fora do escopo |
| Ontologias de projeto (AURORAL, COGITO, BIMERR, DevOps, Transmodel, etc.), corpora de PLN (TINTO, termex, teresia), software FAIR (rsfc, soca, somef, codemeta), blockchain | Fora do escopo do template; algumas servem como exemplos de LOT aplicada, mas não como tools |
| OWL-To-OAS e oatapi | Parados; OATAPI exige CQs com os nomes exatos dos elementos. A ideia de gerar SPARQL a partir de CQs pode inspirar o `eval`, mas sem reuso de código |
